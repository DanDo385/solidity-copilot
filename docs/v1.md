# V1: Task, Data, and Evaluation Contract

## 1. Purpose and boundary

V1 measures constrained Solidity project generation. Given a machine-readable specification, required source files, and optional reference-contract context, a candidate must produce Solidity implementation files, Foundry tests for its claimed behavior, and a short assumptions list.

V1 does not claim autonomous smart-contract engineering, an audit, or deployment readiness. It excludes model training until a retrieval/few-shot baseline demonstrates a stable, data-addressable gap. It also excludes mainnet deployment, private-key handling, secrets, and any corpus item without verified provenance and license terms.

The key words MUST, MUST NOT, REQUIRED, SHOULD, and MAY are normative.

## 2. V1 task contract

### 2.1 Candidate-visible input

The harness materializes one task in an isolated Foundry project. The candidate receives:

1. `task_id` and `schema_version`.
2. An exact compiler target and Foundry profile.
3. A structured specification containing:
   - functional requirements with stable requirement IDs;
   - required interfaces and function signatures;
   - access-control and authorization rules;
   - events and custom errors;
   - state invariants and transition constraints;
   - dependency, file, style, and forbidden-operation constraints.
4. `required_source_files`, each with a repository-relative path, full content, role, and SHA-256 digest. These files are immutable candidate inputs such as interfaces, local libraries, or fixtures. Paths MUST be relative, normalized, and confined to the project root.
5. Optional `reference_context`, consisting of attributable excerpts or complete files that illustrate relevant APIs or project conventions. Reference context is read-only and MUST NOT contain the held-out target or a near-duplicate of it.
6. `public_tests`, when the task intentionally exposes examples or interface checks. Public tests are candidate-visible and are not sufficient to establish behavioral correctness.
7. An allowlist of output paths and dependencies.

Free-form prose MAY supplement the structured fields, but MUST NOT be the sole representation of a scored requirement.

### 2.2 Candidate output

The candidate returns one JSON object:

```json
{
  "schema_version": "1.0.0",
  "task_id": "task_01J...",
  "files": [
    {"path": "src/Example.sol", "content": "// SPDX-License-Identifier: MIT\npragma solidity 0.8.26;\n..."}
  ],
  "generated_tests": [
    {"path": "test/ExampleCandidate.t.sol", "content": "pragma solidity 0.8.26;\n..."}
  ],
  "assumptions": ["Requirement R4 is interpreted as ..."]
}
```

Rules:

- `files` MUST contain every requested target file and MUST NOT write outside the output allowlist.
- `generated_tests` MUST contain at least one test file and MUST NOT replace, edit, import, introspect, or bypass evaluator-owned hidden tests.
- Paths MUST be unique, repository-relative POSIX paths with no `..`, absolute prefix, symlink escape, or control character.
- The harness rejects duplicate JSON keys, unknown top-level fields, oversized outputs, and non-UTF-8 content.
- `assumptions` MAY explain ambiguity but MUST NOT override a stated requirement.
- Markdown fences and explanatory prose outside the JSON object are invalid.

### 2.3 Evaluator-owned material

The dataset stores reference target files and curated tests, but the evaluation view removes them before candidate invocation. The harness mounts after generation:

- `hidden_tests`: curated example, boundary, revert, stateful, and invariant tests;
- machine-checkable constraint assertions; and
- security-analysis configuration.

Candidate-generated tests are executed and scored diagnostically for validity and usefulness. They never substitute for hidden tests and do not contribute to the primary behavioral pass rate.

### 3.1 Record invariants

A validator MUST reject a record when any of these conditions holds:

- the origin is mutable, the Git revision is not a full commit SHA, or an artifact digest does not match its bytes;
- license review is not `approved`, redistribution or modification is false, or required attribution is absent;
- a required, reference, target, or test file lacks immutable artifact provenance;
- the compiler version is a range instead of an exact released version;
- requirement, invariant, artifact, or path identifiers are duplicated or unresolved;
- required target paths and output allowlists disagree;
- hidden tests do not map to at least one requirement or invariant;
- reference context overlaps the target or another held-out target under the contamination rules below.

Local records MAY retain content for reproducibility. A distributable manifest MUST omit source content when upstream license terms require link-only redistribution.

## 4. Dataset splits and contamination controls

### 4.1 Unit of splitting

The unit is `split_group_id`, not a file or generated task. A group contains every item with shared semantic lineage, including:

- files from the same upstream package or contract family;
- forks, mirrors, vendored copies, renamed copies, and translated variants;
- derived prompts, redactions, tests, mutations, and synthetic variants;
- parent and child revisions of the same implementation.

Curators MUST create a canonical lineage map before splitting. Unresolved forks remain quarantined rather than being assigned independently.

### 4.2 Deterministic assignment

V1 uses 80% train, 10% validation, and 10% test by split group. Compute `SHA256("solidity-copilot-v1|" + split_group_id)`, interpret the first 64 bits as an unsigned integer, and divide by `2^64`:

- `[0.0, 0.8)` is train;
- `[0.8, 0.9)` is validation;
- `[0.9, 1.0)` is test.

The split manifest records schema version, seed string, group assignment, record IDs, and dataset-manifest digest. It is frozen before model comparison. Validation MAY guide prompts, retrieval settings, and adaptation; test MUST remain untouched until a configuration is frozen. Report task-family counts and Wilson 95% confidence intervals. If a split lacks enough examples for a task family, collect more licensed groups rather than moving individual records across boundaries.

### 4.3 Contamination checks

Run checks before freezing a manifest and again whenever data or retrieval indexes change:

1. Exact byte SHA-256 and normalized-source SHA-256 across all artifacts.
2. Solidity AST fingerprints after removing comments, source locations, and identifier spelling where safe.
3. Token 5-gram MinHash candidate search followed by exact Jaccard review. Quarantine cross-split pairs at Jaccard `>= 0.80`; manually review pairs at `>= 0.60`.
4. Shared rare-string, test-name, revert-message, and long-literal detection.
5. Fork and repository ancestry resolution from provenance metadata.
6. Prompt/reference-to-target overlap using the same exact, AST, and token checks.
7. A corpus audit that searches every validation/test target and hidden-test digest against training data, few-shot examples, retrieval indexes, caches, and generated artifacts.

For validation and test tasks, retrieval and few-shot examples MUST come only from train groups. The reference context embedded in a held-out record MAY come from its own upstream project only when it is explicitly part of the candidate-visible task and passes target-overlap checks. Hidden tests, reference targets, and test outputs MUST never enter prompts, retrieval indexes, training records, or tuning logs.

Any confirmed cross-split semantic clone moves the entire lineage to one group and forces a new manifest version. Results from a contaminated manifest are invalid, not merely caveated.

## 5. Reproducible evaluation harness

Each run MUST pin and record:

- dataset and split-manifest digests;
- model/provider identifier and immutable revision where available;
- prompt-template and retrieval-index digests;
- decoding parameters, random seed, sample count, and context limit;
- `solc`, Foundry, dependency-lock, static-analyzer, and container image versions;
- wall-clock timeout and CPU/memory/network policy;
- raw candidate output, parser result, build/test logs, and per-check outcomes.

Evaluation runs in a fresh sandbox with no network, secrets, prior build cache, or writable paths outside the task workspace. Dependencies are vendored or fetched before isolation and verified against the lock manifest. The harness evaluates one primary deterministic attempt per task (`temperature = 0` where supported). Optional multi-sample `pass@k` is secondary and MUST report token and attempt cost.

The execution order is:

1. Validate candidate JSON and path/size policy.
2. Materialize immutable required files and candidate outputs.
3. Add evaluator-owned hidden tests without exposing their content to the candidate.
4. Run `forge build --force` under the pinned profile.
5. Run public, candidate-generated, and hidden test suites separately.
6. Run deterministic constraint checks.
7. Run the pinned static analyzer and store normalized findings.
8. Route the predefined manual-review sample for blinded security triage.

Harness errors are reported separately and do not count as candidate failures until rerun successfully.

## 6. Metrics

All primary rates are macro-averaged over tasks and reported as numerator, denominator, percentage, and Wilson 95% confidence interval. Also report each task family separately. A task succeeds only on its primary deterministic attempt.

### 6.1 Forge compile rate

`compiled_tasks / evaluable_tasks`

A task compiles only if candidate output parses, all required target files exist, and `forge build --force` exits zero with the pinned compiler and dependencies. Harness failures are excluded and enumerated; candidate timeouts and invalid outputs are failures.

### 6.2 Hidden-test pass rate

Primary: `tasks_with_all_hidden_tests_passing / compiled_tasks`.

Secondary: `passing_hidden_test_cases / executed_hidden_test_cases` and end-to-end `tasks_with_all_hidden_tests_passing / evaluable_tasks`.

Public and candidate-generated tests are reported separately. Candidate-generated-test diagnostics include compile rate, pass rate against the candidate implementation, requirement-ID coverage, and mutation score when a fixed mutation set exists.

### 6.3 Constraint compliance

Report both:

- check rate: `passed_required_constraint_checks / executed_required_constraint_checks`;
- strict task rate: `tasks_passing_every_must_constraint / evaluable_tasks`.

Checks are keyed to stable requirement IDs and include ABI/signature, visibility, inheritance, event/error, authorization, forbidden opcode/operation, dependency, path, and invariant assertions. Ambiguous requirements are dataset defects and must be repaired, not manually awarded.

### 6.4 Security-oriented triage

This is triage, not proof of security. Report:

- analyzer completion rate;
- new unallowlisted findings per 1,000 nonblank Solidity lines by severity;
- tasks with any new high/critical finding;
- hidden security-test pass rate;
- blinded manual-review counts by severity and category; and
- false-positive adjudications with reviewer agreement when two reviewers are available.

The tool version, configuration, detector set, suppressions, and baseline allowlist MUST be pinned. A baseline comparison is security-regressed if it increases tasks with confirmed high/critical findings or reduces hidden security-test pass rate, regardless of aggregate compile gains.

### 6.5 Failure taxonomy and cost

Every failure receives one primary category: output protocol, Solidity syntax/type, dependency/import, requirement misunderstanding, authorization, invariant/state transition, test-generation, timeout/resource, security, or harness. Report prompt/completion tokens, latency, and estimated cost per task. These diagnostics determine whether a gap is retrieval-addressable, prompt-addressable, data-addressable, or unrelated to model adaptation.

## 7. Baselines and LoRA/QLoRA decision rubric

Evaluate the same frozen validation set, model revision, token budget, and harness with:

- `B0`: structured prompt only;
- `B1`: structured prompt plus fixed train-only few-shot examples;
- `B2`: structured prompt plus train-only retrieval and the same few-shot budget.

Tune baseline configuration on validation only. Freeze the best baseline before one final test run.

### 7.1 Readiness gates for any adaptation experiment

Do not begin LoRA or QLoRA unless all gates pass:

1. Data legality: 100% of proposed training records pass provenance, digest, and license validation.
2. Split integrity: zero unresolved exact, AST, lineage, or `>= 0.80` token-similarity leaks; every `>= 0.60` candidate is adjudicated.
3. Harness reliability: two clean reruns produce identical parser/build/test/constraint outcomes, excluding documented provider nondeterminism.
4. Baseline completeness: B0, B1, and B2 have complete validation reports using identical budgets.
5. Gap stability: at least 25 validation tasks fail the target metric, and the same primary failure categories recur across two baseline reruns.
6. Data addressability: at least 30% of baseline failures belong to categories represented by multiple independent, licensed train groups. Pure retrieval misses, ambiguous specs, harness defects, and security-review uncertainty do not qualify.

If any gate fails, improve the data, task specification, retrieval, or harness instead of fine-tuning.

### 7.2 Decision table

| Observed result | Decision |
| --- | --- |
| B2 reaches at least 95% compile rate, 80% end-to-end hidden-test task pass rate, 95% strict constraint compliance, and has no security regression | Keep retrieval/few-shot. LoRA is not justified for V1. |
| B2 improves the target metric by at least 5 percentage points over B1, or removes at least 25% of B1 failures in the dominant category | Improve retrieval/context construction before considering LoRA. |
| Failures are mostly missing facts, unavailable APIs, ambiguous requirements, or long-context selection errors | Fix task/data/retrieval design. Do not use LoRA as a memory patch. |
| B2 remains below a quality threshold, all readiness gates pass, and the dominant gap is a repeated train-represented Solidity/Foundry or constraint-following behavior | Approve one bounded LoRA pilot. |
| A LoRA pilot fits available memory only through quantized loading while preserving the same data and evaluation contract | Use QLoRA as an implementation method, not as a separate product hypothesis. |
| Adaptation improves compilation but weakens hidden tests, strict constraints, or security triage | Reject the adapted model. Compilation-only gains do not qualify. |

### 7.3 Promotion criterion for an adaptation pilot

Choose hyperparameters on validation without consulting test. Freeze one adapter, then compare it once with the frozen B2 baseline on test. Promote only if it:

- improves end-to-end hidden-test task pass rate by at least 5 percentage points;
- does not reduce Forge compile rate or strict constraint compliance by more than 1 percentage point;
- introduces no security regression as defined above; and
- documents training compute, data-manifest digest, adapter/config digest, inference cost, and confidence intervals.

If the test set has fewer than 100 tasks, percentage-point thresholds are descriptive only; require paired bootstrap confidence intervals and manual review before making a claim. A failed pilot returns V1 to retrieval/few-shot rather than triggering an unbounded tuning loop.

## 8. Proposed next task graph

This is a proposal, not permission to collect data or train a model.

```text
A. Version JSON Schemas and validators
   ├── B. Build licensed provenance-manifest pipeline
   └── C. Build candidate I/O parser and sandbox fixture

B ──> D. Curate a small licensed seed corpus and lineage map
D ──> E. Implement split manifest and contamination audit

C ──> F. Implement Forge compile/test/constraint harness
F ──> G. Add pinned static analysis and manual-review rubric

E + F + G ──> H. Assemble frozen validation benchmark
H ──> I. Run B0/B1/B2 retrieval and few-shot baselines
I ──> J. Publish baseline report and apply the decision rubric

J ──> K1. If gates fail: repair task/data/retrieval/harness, then rerun H-I
J ──> K2. If every adaptation gate passes: write a bounded LoRA/QLoRA pilot plan
K2 ──> L. Separate approval task for any training run
```

Suggested ownership and acceptance boundaries:

- A: schema/validation engineer. Deliver schemas, valid/invalid fixtures, and deterministic validator tests.
- B and D: data curation/legal-review owner. Deliver only approved, attributable manifests; no bulk unlicensed collection.
- C, F, and G: evaluation engineer plus security reviewer. Deliver a network-isolated, version-pinned harness with synthetic fixtures before real corpus use.
- E: data/evaluation engineer. Deliver frozen split manifests, contamination reports, and quarantined-pair adjudications.
- H and I: evaluation owner. Deliver immutable run manifests and raw results; no tuning on test.
- J: independent reviewer. Verify the evidence and record retrieval-versus-adaptation decision.
- K2 and L: ML engineer then explicit operator approval. Planning and execution remain separate gates.

## 9. V1 exit evidence

V1 is ready for implementation work when sections 2 through 7 are represented by versioned schemas, validators, fixtures, and harness tests. It is ready for a model comparison only after a frozen legal dataset and contamination report exist. It is ready for a LoRA/QLoRA decision only after the B0/B1/B2 report is reproducible under this contract.
