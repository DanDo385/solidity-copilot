# V1: Task Definition and Evaluation Contract

## Product boundary

V1 investigates constrained Solidity code generation. It does not claim autonomous smart-contract engineering and it does not deploy contracts.

The initial task shape is:

```text
Input:
- structured functional specification
- compiler target and dependency allowlist
- optional reference-contract snippets
- explicit interfaces, access-control rules, and invariants

Output:
- Solidity source files
- a short assumptions note
- Foundry tests for claimed behavior
```

The exact input representation remains an early research decision. Natural-language-only prompts are insufficient for rigorous evaluation because they leave too much room for ambiguous requirements.

## Dataset record

Each JSONL example should use a structure equivalent to:

```json
{
  "id": "stable-unique-id",
  "license": "SPDX identifier or documented terms",
  "source": {"repo": "owner/repo", "commit": "immutable revision", "path": "src/Example.sol"},
  "solc_version": "0.8.x",
  "task": {
    "spec": "Structured functional requirements",
    "interfaces": ["interface declarations or identifiers"],
    "invariants": ["properties that must hold"],
    "constraints": ["dependency, gas, or style constraints"]
  },
  "reference_context": ["optional snippets, never a held-out target leak"],
  "target": {"files": [{"path": "src/Example.sol", "content": "..."}]},
  "tests": [{"path": "test/Example.t.sol", "content": "..."}]
}
```

No source may enter the corpus without provenance, license metadata, and a pinned source revision.

## Evaluation gates

Every candidate must be scored against held-out examples never used for prompting or training:

1. Parse and compile: `forge build` with the expected compiler target.
2. Behavioral correctness: `forge test` against curated and generated tests.
3. Constraint compliance: interface, visibility, event, and invariant checks.
4. Security-oriented triage: static-analysis findings plus a manual review sample.
5. Contamination checks: deduplicate near-identical examples across train, validation, and test splits.

Compilation alone is not success. It only proves the program is grammatically alive.

## Baseline gate before fine-tuning

Run a base-model benchmark using retrieval and few-shot examples first. Record compile rate, test-pass rate, and common failure categories.

Proceed to LoRA or QLoRA only when the baseline report identifies a stable, data-addressable gap. Candidate gaps include:

- recurring Foundry or Solidity idiom failures;
- inconsistent conventions within a defined contract family;
- poor use of structured constraints; or
- insufficient accuracy on the target task distribution.

## Non-goals for V1

- Mainnet deployment.
- Private-key handling.
- Production security guarantees.
- Training on unlicensed or provenance-free contract corpora.
- Claims that generated code is audited.
